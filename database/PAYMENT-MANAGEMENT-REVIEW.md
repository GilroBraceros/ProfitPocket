# Payment Management revision

Implemented on 18 October 2026. Open `user/payments.php` through the owner sidebar.

## Scope and preserved features

The former credit-only page is now a payment ledger browser and balance manager.
It includes initial full payments, downpayments, later partial/final payments,
walk-in sales, named customers, mixed payment methods and outstanding balances.
Existing credit history, partial repayments, settlements, overdue monitoring,
due-date editing, audit history, archived-customer balances and duplicate protection
are preserved. Original logos and established owner/admin layouts remain in use.

`user/utang.php` redirects authenticated owners to Outstanding Balances, preserving
recognized search/status/customer/date parameters. `user/utang_action.php` remains
an authenticated compatibility endpoint. Internal `utang:*` idempotency prefixes,
signed action names, legacy report query keys and credit table names are retained
so they do not invalidate existing records or create another ledger.

## Database inspection and approved change

The existing schema, live columns, primary/foreign keys, financial views, payment
methods and application flows were inspected. A read-only inspection report is
generated by `tests/payment_schema_inspect.php` under protected `tests/http-results/`.

| Relationship | Existing source |
| --- | --- |
| Business owner | `businesses.owner_user_id` → `users.user_id` |
| Customer ownership | `customers.business_id` → `businesses.business_id` |
| Sale ownership/customer | `sales.business_id`; composite `(customer_id,business_id)` foreign key |
| Purchased items | `sale_items.(sale_id,business_id)` → `sales` |
| Received money/refunds | `sale_payments.(sale_id,business_id)` → `sales` |
| Payment method | `sale_payments.payment_method_id` → `payment_methods.payment_method_id` |
| Recorder | Composite business/owner foreign key on `sale_payments.(business_id,entered_by)` |
| Refund relationship | `reverses_payment_id` references a collection on the same sale/business |
| Credit due date/notes | `customer_credits.sale_id` → `sales.sale_id`, one row per credit sale |
| Financial calculations | `v_payment_totals`, `v_sale_financials`, `v_daily_financials` and existing audit triggers |

The existing methods were Cash, GCash, Maya and Bank Transfer. The schema already
had payment dates, DECIMAL amounts, references, notes, recorder, refund links,
immutable histories and unique business/idempotency keys. It lacked provider/bank
metadata and an Other-wallet method.

The owner explicitly approved `database/payment-provider-proposal.sql`. It was
applied once: one nullable `sale_payments.provider_name VARCHAR(80)` column and one
`payment_methods` row (`wallet_other`, Other Digital Wallet). The provider column
stores a wallet/bank name associated with the existing method foreign key. No
structured metadata is hidden in notes or references. Existing rows remain NULL;
GCash/Maya names can also be derived from their historical method codes. Old bank
names are displayed as Not recorded rather than invented.

No table was recreated, renamed, dropped or truncated. No payment amounts,
historical sale items, foreign keys, views or triggers were rewritten. The SQL
reference now includes the approved column. The migration file is a deployment
reference, not an automatic page-load migration.

## Features and interface

- Four cards show period valid collections and current outstanding, partially paid
  sale count and fully paid sale count. Balance/count cards explicitly cover all
  sale dates. Collection cards and method summaries use payment dates.
- Payment History shows date/time, customer, sale reference, derived type, method,
  provider and amount, with search, date/method/type filters and 15-row pagination.
  View opens complete recorded metadata; the compact menu opens the sale details
  or its complete payment history.
- Outstanding Balances shows original sale, total paid, balance, due date, status
  and compact actions. It supports customer/reference search, payment-state and
  overdue filters, due-date sorting, audited due edits and additional collections.
  The paid/all options expose settled valid sales without removing debt tracking.
- Record Payment shows the actual customer/reference and financial totals, amount,
  method-specific fields, Philippine date/time, optional notes and an exact
  centavo preview. Cash hides wallet/bank/reference fields. Digital Wallet offers
  GCash, Maya and Other; Other requires a name. Bank Transfer requires a bank name.
  Wallet/bank reference numbers are optional because the existing column is nullable.
- The same method controls are used in Add Sale. Its existing item/discount layout
  remains intact. Full Payment, Downpayment / Partial Payment and Unpaid determine
  the initial payment and any existing customer-credit relationship. Payment notes
  are stored separately from sale notes.
- Desktop uses the established forest/neutral owner styling. Tablet/phone tables
  become labelled records; phone cards stack and payment dialogs become fullscreen.
  Focus, validation, loading/saving, duplicate-click and unsaved-change behavior are
  retained. No additional library, chart, logo, email or gateway integration was added.

## Classification, refunds and financial rules

The immutable `payment_id` recording order determines payment type. The first
collection is Full Payment if it settles the sale, otherwise Downpayment. Later
collections are Partial Payment until one settles the then-current net balance,
which is Final Payment. Refunds reduce the running paid amount. Backdating a
payment changes chronological display and reporting dates, not which collection
was first. SQL filters and PHP detail/history classifications were checked against
the same transactions.

History/collection totals include posted sales and the unreversed portion of each
collection. Voided sales, drafts, refund rows and fully reversed collections are
excluded from received-payment totals. Partially refunded payments show the retained
amount in the list and both original/refunded amounts in details. Complete per-sale
history still preserves every original collection and refund.

These are **currently valid collections grouped by their original payment dates**.
A later refund can reduce a previous period's valid-collection figure. Existing
cash-flow reports continue to account for collections and refunds on their actual
event dates; that is a separate measure. No historical as-of balance is claimed.

BCMath/DECIMAL-compatible calculations, transaction/business/sale locks, current
locking reads and the existing database overpayment trigger protect collections.
Amounts must be positive, have at most two decimal places and fit the current
balance. Dates cannot precede the sale or be in the future. Prepared statements,
live owner authorization, business scoping, CSRF and signed action/record tokens
are enforced. The existing unique durable key prevents duplicate financial writes.
Payment types are derived, not accepted as user-entered financial facts.

## Connected modules

- **Sales:** initial method/provider/reference/notes are stored on the same ledger;
  sale amounts, discounts and item snapshots remain unchanged by repayments.
  Existing whole-sale voids copy provider metadata to the linked refunds.
- **Customers:** valid purchase totals, net paid, outstanding balances, statuses and
  recent payment events are shown, with a link to the customer's payment view.
- **Dashboard:** the existing current balance and recent activity include payments
  on all sale types. A compact valid-collections line links to the selected period.
- **Reports:** current receivables include any reopened unpaid balance, while a
  compact collection-method line links to Payment Management. Receivables labels
  and CSV filenames replace the old user-facing Utang terminology. Existing credit
  collection cash-flow subtotals are explicitly labelled as credit collections.
- **Refund edge case:** a partial refund on an originally fully paid immediate
  sale reopens a balance. Payments, Customers, Dashboard and Receivables now include
  that balance consistently, without inventing another credit record.
- **Admin, expenses, products and authentication:** existing functionality and
  authorization remain in place; no unrelated redesign or calculation change.
